# 设计：视频工程层 + 风格参考

**状态**：原型已实现并验证（Phase 1），见第九节。代码在 `toolkit/vlab/videokit/`，演示在 `research/visual/08-video-spec/`。
**起因**：参考 Fotor Agent 的思路（代码渲染 + 可编辑工程 + 风格参考），结合我们"先配音、后画面"的流水线。

---

## 背景：现在的痛点

现在一条视频的信息分散在三处：

| 位置 | 内容 | 问题 |
|---|---|---|
| `content/xxx.json` | 旁白、标题 | 只有文字 |
| `build/xxx/timeline.json` | 词级时间点 | 自动生成，没问题 |
| `manim/scene.py` 等代码 | **画面上的文字、数字、颜色、位置、出场时机全写死在代码里** | 改一个数字、换一个颜色、挪一点位置都要改代码重渲染全片 |

结果：

- 改文案、改数据这种最高频的修改，成本和写新功能一样高；
- 换风格要逐个文件改颜色；
- 改一处要重渲染整条视频（001/002 全片渲染 3–10 分钟）；
- AI 改代码容易"顺手"改坏别的地方。

## 目标

1. **改内容不改代码**：文案、数字、颜色、出场时机、位置微调都在一个工程文件里改。
2. **换风格不改代码**：风格是一份独立的设计规范文件，换文件就换整体风格。
3. **风格可以从参考视频里提取**：给一段喜欢的视频，自动分析出配色、节奏，AI 再整理成规范。
4. **只重渲染改动的镜头**：按镜头缓存，改一个数字只重出那一个镜头。
5. **不丢掉现有能力**：Manim、着色器、程序化风景这些"定制镜头"照样能用。

非目标（本期不做）：可视化拖拽编辑器、像素级生成模型接入。

---

## 一、三层结构

```
内容层   说什么、显示什么        旁白、标题、数据、引用哪种颜色          ← 人 / AI 改工程文件
编排层   什么时候、放在哪        元素"在说到哪个词时出现"、位置微调      ← 人 / AI 改工程文件
表现层   长什么样、怎么动        模板代码 + 风格文件（设计规范）         ← 偶尔改
```

关键约束：**编排层绑定到"词"而不是"秒"**。改稿子重新配音后，时间点自动跟着走；
某个词从稿子里删掉了，校验会直接报错，不会悄悄错位（沿用 001–003 的做法）。

## 二、工程文件 `project.yaml`

```yaml
id: spec-demo
title: 天空为什么是蓝的
style: styles/landscape.yaml          # 风格文件；命令行 --style 可临时换
voice: {name: zh-CN-YunxiNeural, rate: "+8%"}

scenes:
  - id: compare
    template: bar_compare              # 用哪个模板（模板库见第三节）
    narration: 蓝光被散射的强度，差不多是红光的六倍。
    params:                            # 模板参数 = 画面上的内容
      title: 蓝光散射约为红光 6 倍
      bars:
        - {name: blue, label: 蓝光 450 纳米, value: 5.86, color: accent2}   # color 引用风格里的颜色名
        - {name: red,  label: 红光 700 纳米, value: 1.0,  color: accent1}
      callout: ≈ 5.9 倍
    cues:                              # 编排：元素名 → 在哪个词出现
      bars.blue: {on: 蓝光}
      bars.red:  {on: 红光, anim: grow}
      callout:   {on: 六, anim: pop}
    overrides:                         # 精修：位置、缩放、颜色微调（相当于剪辑软件里拖一下）
      callout: {dy: 0.3}
```

字段规则：

| 字段 | 说明 |
|---|---|
| `template` | 模板名；`custom` 表示走定制代码（逃生口，见第三节） |
| `params` | 模板需要的内容；文字、数字、颜色名 |
| `cues.<元素>.on` | 出现时机绑定的词；可加 `nth`（第几次出现）、`offset`（秒）、`anim`（入场方式） |
| 没写 cue 的元素 | 镜头开始时按风格里的节奏依次出现 |
| `overrides.<元素>` | `dx`/`dy`（画布单位）、`scale`、`color` |
| 颜色 | 一律写风格里的名字（`ink`、`accent1`…），也允许直接写 `#rrggbb` |

## 三、模板库 + 逃生口

- **模板**：一类常见画面写一次代码，参数化复用。原型实现了三个：
  `title_card`（标题卡）、`bar_compare`（数值对比柱）、`bullet_list`（要点列表）。
  模板负责布局，把每个元素按名字登记（如 `title`、`bars.blue`、`items.0`），供编排层引用。
- **逃生口**：`template: custom` 指向一段定制代码（如 003 的大气散射着色器、莫比乌斯环）。
  定制镜头也从工程文件读文案和颜色，只是布局和动画在代码里。
  —— 这样 80% 的常规镜头走模板、改数据不碰代码；20% 的"惊艳镜头"照样手写。
- 后续可加：`big_number`、`line_chart`、`timeline`、`quote`、`image_parallax`（见第六节分层）。

## 四、风格文件 `style.yaml`（设计规范）

```yaml
name: landscape-sunset
palette: {bg: "#1b1636", bg2: "#3d2a7a", ink: "#fff1e6", dim: "#b9a3c9",
          accent1: "#ff9f80", accent2: "#8fa8ff", accent3: "#ffd27a"}
font: {family: Microsoft YaHei, title_size: 56, body_size: 40}
layout: {title_y: 5.6, content_y: 1.2}
motion: {enter: fade_up, duration: 0.5, stagger: 0.12, easing: smooth}
texture: {vignette: 0.3, grain: 6}      # 后期质感，拼接时用 ffmpeg 统一加
```

模板只认这些名字，不写死任何颜色、字号、动画时长。

## 五、风格参考：从一段视频里提取风格

```
参考视频 ──► ① 代码分析（客观指标） ──► ② AI 看图整理（主观判断） ──► style.yaml ──► ③ 对比验收
```

1. **代码分析**（`style_extract.py`，确定性、可复现）：
   - 镜头切换检测 → 镜头数、平均镜头时长（剪辑节奏）；
   - 均匀抽帧 + 切换点抽帧 → 拼成一张总览图；
   - 主色提取（k-means）→ 色板及占比、亮度、饱和度；
   - 画面运动量（相邻帧差）→ 动效快慢；
   - 自动给出一份**草稿**风格文件（最暗的大面积色当背景、最亮的当文字、最饱和的几个当强调色、按节奏定动画时长）。
2. **AI 整理**：AI 看总览图和指标，修正草稿（比如草稿把天空的米色当成文字色，AI 改成更易读的颜色；
   判断"逆光剪影"这类主观风格并写进备注）。
3. **对比验收**：用新风格渲染一遍，和参考视频的总览图并排看。

只提取抽象风格（配色、字号层级、节奏），**不复制参考视频里的任何内容和素材**。

## 六、构建与增量渲染

```
project.yaml ─► 校验 ─► 配音（旁白没变就跳过）─► 逐镜头渲染（指纹没变就跳过）─► 帧数校验 ─► 拼接 + 质感 ─► 合配音字幕
```

- **校验**（渲染前）：模板存在、必填参数齐全、cue 绑定的词在旁白里、颜色名在风格里。错误一次全列出来。
- **镜头指纹** = 该镜头的工程内容 + 风格 + 它在时间轴上的起止和词 + 模板代码的哈希。
  指纹没变就复用上次的片段；改一个镜头的数字，只有这个镜头重渲染。
- **帧数**：每个镜头的帧数 = round(结束×fps) − round(开始×fps)，拼起来正好等于配音长度（沿用 003 的做法）。
- 风格不同的片段分目录缓存，两种风格可以并存、来回切换不用重渲染。

## 七、AI 在这套结构里怎么工作

| 用户说 | AI 改什么 | 影响范围 |
|---|---|---|
| "把 5.9 倍改成 6 倍" | `params.callout` | 只重出 1 个镜头 |
| "数字晚一点出来，等说到'六'" | `cues.callout.on` | 只重出 1 个镜头 |
| "这个标签往上挪一点" | `overrides.callout.dy` | 只重出 1 个镜头 |
| "整体换成这个视频的感觉" | 跑风格提取 → 写新 `style.yaml` | 全部镜头（旧风格缓存保留） |
| "加一个讲 XX 的镜头" | 新增一个 scene，选模板填参数 | 新镜头 + 重新配音 |
| "做一个莫比乌斯环翻面" | 写定制代码（逃生口） | 只有这个镜头 |

好处：AI 改的是结构化数据，改动范围清楚、可校验、git diff 一目了然；不会改一个数字顺手改坏动画代码。

### 实测（GTX 1060 机器，23 秒、3 个镜头的演示）

| 操作 | 结果 | 用时 |
|---|---|---|
| 改了模板代码 | 3 个镜头全部重渲染 | 84 秒 |
| 什么都不改再构建 | 全部复用，跳过拼接 | 1 秒 |
| 只改一个镜头的文案和位置（两行 YAML） | 只重渲染这一个镜头 | 47 秒 |
| 换成另一份风格文件 | 3 个镜头并行渲染 | 44 秒 |
| 再换回原风格 | 两种风格缓存并存，直接复用 | 2 秒 |

风格对比见 `research/visual/08-video-spec/renders/style_compare.png`。

### 测试中发现并修掉的问题

1. **YAML 把 `on` 当成布尔值**：`{on: 蓝光}` 被读成 `{True: 蓝光}`，所有按词出场的设置被悄悄忽略，校验还"通过"了。
   用一份故意写错的工程做反例测试才发现。改为只认 `true/false` 为布尔值，并校验出场/微调字段名拼写。
2. **配音的分词和我们想的不一样**："四次方"被切成 四/次/方，"越短"被切成 越/短。
   配音后第二道校验把三处全部找出来并列出可用的词，改绑定即可，不用改旁白。
3. **拼接编码比渲染还慢**：全部复用时仍要 69 秒。中间文件改用最快编码、加"总装指纹"后降到 1 秒（无变化）/ 35 秒（需拼接）。
4. **草稿风格可读性差**（符合预期）：湖景草稿把和背景同色的深紫当强调色，云海草稿文字和背景对比太低。
   这正是"AI 看图修正"这一步存在的原因；修正理由写在两份风格文件的注释里。

### 局限（留给后续阶段）

- 模板只有 3 个、只有 Manim 一种渲染器；着色器、程序化风景还不能作为 `custom` 镜头接入（Phase 2）。
- 微调只支持位移、缩放、颜色；不支持改动画曲线和时长的单镜头覆盖。
- 风格提取只看颜色、明暗、节奏，不识别字体和具体动效形式；这部分靠 AI 看总览图判断。
- 拼接后的质感（暗角、颗粒）作用于整片，不能按镜头关掉。
